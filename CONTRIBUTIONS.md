# My Contributions

Team project (myself + one teammate). This document covers only the parts I
personally designed and built, written to stand on its own — pull chunks straight
into a resume bullet or an interview answer.

## 1. Prompt-variant system: a Thompson Sampling multi-armed bandit (headline project)

**The problem:** the team wanted the AI's response quality to improve from user
feedback, the way "reinforcement learning" usually implies. But the app calls the
closed-source Anthropic API — there's no model to fine-tune. So "learning" has to
happen one layer up, at the prompt.

**The approach:** I designed and built a system where each avatar can have several
*prompt variants* (small additions appended to its base system prompt). Every reply
is generated by one variant, chosen by a Thompson Sampling multi-armed bandit — each
variant keeps a Beta(α, β) posterior over its "success rate" (👍 = success,
👎 = failure); the bandit draws a sample from each variant's posterior per
conversation and picks the highest draw. This balances exploring untested variants
against exploiting the one that's currently winning — a fixed-schedule A/B split
would either waste traffic on a clearly-worse variant for too long, or take longer
to converge.

What I built:

- `PromptVariant` model with live α/β, wired through `chat_service` (variant
  selection) and `feedback_service` (posterior updates, including safely reversing
  a stale reward when a user changes their 👍 to a 👎)
- A `Baseline` variant is auto-created the first time an avatar gets any variant, so
  the bandit always has the unmodified original prompt as a control
- REST API to create/list/enable/disable variants with live stats
- A **Thompson Sampling vs. epsilon-greedy vs. random simulation**, run over 300
  independent trials (a single run was too noisy to show real convergence),
  producing an interactive report comparing cumulative regret and
  variant-selection convergence over time
- The admin UI — a page per avatar to create variants, toggle them on/off, and
  watch their live approval rate — verified end to end by hand: variants appear
  weighted by their posterior, and the higher-approval variant's selection share
  visibly climbs over a session

**Engineering notes worth mentioning in an interview:**

- Caught a subtle SQLAlchemy trap: `func.case(...)` silently fails; `case()` needs
  its own import.
- Traced a bug where backend 500 errors *looked* like CORS failures in the browser
  (the error response was missing CORS headers) — a reminder to always check the
  actual server stack trace, not just the browser console.
- The simulation itself taught a real statistics lesson: a single simulated run is
  noisy enough to show a *worse* variant "winning" by chance; only averaging over
  many independent runs shows the algorithm working as designed.

## 2. Retrieval-augmented generation, built from zero

The team assumed the app "already had RAG." Checking the code showed uploaded files
were just being dumped whole into the conversation context (context-stuffing) — not
retrieval at all, and it didn't persist past a single chat session. I designed and
built the real thing, persisted per avatar rather than per session:

- `DocumentChunk` model — files are split into 800-character chunks with 100
  characters of overlap, embedded, and stored with the avatar (not the session)
- `rag_service`: chunking, embedding, indexing, and top-4 retrieval above a 0.2
  similarity threshold — brute-force cosine similarity, deliberately, since at this
  data scale a dedicated vector database would be over-engineering
- Wired into `chat_service`: relevant chunks are retrieved and injected into the
  system prompt before every reply; the SSE `message_done` event returns which
  sources were used so the frontend can show a "📚 referencing: filename" tag

**Two real bugs found and fixed along the way (good debugging stories):**

1. **PDF text was gluing words together** (`"Atwo-stage"`, `"SchoolofOptical"`) —
   `PyPDF2`'s extraction doesn't preserve word boundaries reliably, which quietly
   degraded embedding quality. Found by inspecting the actual stored chunks in
   SQLite, not by any error message. Fixed by switching to `PyMuPDF` (`fitz`) for
   layout-aware extraction, with a regex fallback (`_fix_glued_words()`) kept as a
   safety net.
2. **Cross-language retrieval silently returned nothing.** The embedding model
   (`all-MiniLM-L6-v2`) is English-only; a Chinese question against an English PDF
   never scored above the similarity threshold, so retrieval returned empty with no
   error at all — the avatar just said it hadn't received the file. There was no
   stack trace to follow; the only way to find it was comparing expected vs. actual
   behavior end to end. Switching to a multilingual model
   (`paraphrase-multilingual-MiniLM-L12-v2`, 50+ languages) fixed it — verified with
   a fresh conversation, a Chinese question, and a correct citation back to the
   English source PDF.

## 3. Account system: three product gaps closed in one pass

While preparing this project for review, I found the account experience had three
real gaps — not obscure edge cases, but things any user would hit immediately —
and closed all three:

- **Chat sessions were never named.** Every session showed as generic "New Chat,"
  which also made switching avatars look like nothing had changed (the list *was*
  updating — every title just looked identical). Fixed with automatic naming from
  a session's first message (ChatGPT-style) plus a `PATCH` endpoint and a
  double-click-to-rename UI, so either the system or the user can set the title.
- **No way to recover a forgotten password.** Built a full flow against a real
  transactional email provider (Resend): a one-time, one-hour-expiry token, a
  `forgot-password` / `reset-password` page pair, and an endpoint deliberately
  designed to return the same response whether or not the email is registered — so
  the API can't be used to enumerate which addresses have accounts.
- **No profile editing.** Added an endpoint and page to update username, email, or
  password (a password change requires re-entering the current one first).

**A debugging story worth telling:** testing the password-reset flow produced a
403 from Resend with no immediately obvious cause. It turned out free/unverified
Resend accounts can only send to the account owner's own signup address — sending
to any other address is rejected outright. The first test had actually failed
silently for an unrelated reason (the anti-enumeration design means "email not
found" and "email sent" look identical to the client, and the test address simply
wasn't registered); the second test hit the real Resend restriction. Diagnosing it
meant reasoning about two independent failure modes that produced the same
symptom, on a system deliberately designed not to reveal which one occurred.

## 4. Feedback pipeline

Designed and built the app's feedback loop end to end:

- `MessageFeedback` model + `POST /api/feedback/{message_id}` (thumbs up/down,
  upsertable — a user can change their mind and the count stays correct)
- `GET /api/feedback/summary`, aggregated per avatar
- A `/feedback` dashboard showing overall + per-avatar approval rate
- Verified end to end: click → API → DB → aggregation query → UI, all consistent

This pipeline is also what feeds the bandit in section 1 — every reply's feedback
resolves back to the specific prompt variant that generated it.

## 5. Product design & UI

Redesigned the app's default look into a "casting call" theme — Fraunces serif
display font, a turquoise/terracotta accent palette, three switchable themes
(Matinee light / Midnight dark / Sepia), persisted per user. Later also reworked
the chat sidebar so each avatar's chat history nests under it and expands/collapses
independently on click, rather than showing every avatar's sessions flattened
together. Started as an independent learning exercise (my own Next.js/Prisma/Git
practice branch) before being folded into the shared frontend.

## 6. Testing & QA process

Set up and ran the project's testing process from scratch: a living `TESTING.md` →
`TESTING2.0.md` covering 5 structured test sessions across the app's full surface
(auth, chat streaming, file uploads, mastery tracking, feedback). Found and logged
10 issues over the project's life, including a topic-mastery tracking regression
and a corrupted-session state that locked users out of chat. Also resolved a Git
merge conflict in the test doc itself without losing either side's test history.

---

*Stack across all of the above: FastAPI + SQLAlchemy (async) + SQLite on the
backend, Next.js 14 + TypeScript + Tailwind on the frontend, JWT auth, and the
Anthropic Claude API for inference — no model training anywhere; every "learning"
mechanism above operates at the prompt or the retrieval layer.*
